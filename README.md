# SBOM Dashboard

A dashboard for software bills of materials (SBOMs) across many applications and libraries.

- **Upload** CycloneDX or SPDX JSON SBOMs from GitHub Actions (or `curl`).
- **Applications:** every app or library that has uploaded an SBOM, with its vulnerability and update status.
- **Packages:** every package used across the latest SBOM of each application, which versions are in use, and by whom.
- **Vulnerabilities:** known CVEs/advisories for those packages from [OSV.dev](https://osv.dev), with severity, CVSS score and the version that fixes them.
- **Known exploited:** vulnerabilities in the [CISA KEV catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) are flagged so you can fix what attackers actually use first.
- **Exploit likelihood:** each CVE shows its [EPSS](https://www.first.org/epss/) score, the estimated chance of exploitation in the next 30 days.
- **Outdated packages:** the latest release of each package from [deps.dev](https://deps.dev), classified as a major, minor or patch update.

## Stack

| Layer | Choice |
|---|---|
| App | Next.js (App Router) + TypeScript, self-hosted |
| UI | MUI, MUI X DataGrid (MIT), Recharts |
| Database | Postgres via Drizzle ORM; SQL migrations generated by drizzle-kit |
| Worker | Separate Node process that enriches packages from OSV.dev and deps.dev |
| Validation | Zod (env config, upload metadata, SBOM documents, external API responses) |
| Tests | Vitest (unit + API against in-process Postgres via PGlite), Playwright (e2e) |

```
GitHub Action ──POST /api/v1/sboms──▶ Next.js app ──▶ Postgres ◀── worker ──▶ OSV.dev (CVEs)
                                         ▲            (NOTIFY)              └─▶ deps.dev (latest versions)
                               browser ──┘
```

Postgres is the contract between the app and the worker. An upload stores the SBOM and its package versions with an empty
`vulns_checked_at` / `latest_checked_at`, then sends `NOTIFY sbom_uploaded`. The worker processes every row that was never
checked or is older than its TTL, and re-scans everything periodically so newly published CVEs show up without a new upload.
Because the worker only reads and writes tables, it can be replaced (a job queue, or a Python service) without touching the app.

## Quick start

### Docker Compose

```sh
docker compose up --build
```

Open http://localhost:3000. Compose starts Postgres, applies migrations, then runs the web app and the worker.

### Local development

Requires Node 22+ and a Postgres 16 database.

```sh
pnpm install
cp .env.example .env.local          # adjust DATABASE_URL
export DATABASE_URL=postgres://sbom:sbom@localhost:5432/sbom
pnpm run db:migrate
pnpm run db:seed                     # optional demo data (add -- --offline to enrich it without network access)
pnpm run dev                         # http://localhost:3000
pnpm run worker                      # in a second terminal
```

## Uploading SBOMs from GitHub Actions

This repository is also a composite action. Add a workflow to each application repository:

```yaml
# .github/workflows/sbom.yml
name: SBOM
on:
  push:
    branches: [main]
    tags: ['v*']
jobs:
  sbom:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: jsundquist/sbom@main
        with:
          dashboard-url: ${{ vars.SBOM_DASHBOARD_URL }}
          api-token: ${{ secrets.SBOM_DASHBOARD_TOKEN }}   # only needed when UPLOAD_TOKENS is set
```

| Input | Default | Description |
|---|---|---|
| `dashboard-url` | (required) | Base URL of the dashboard |
| `api-token` | `''` | Bearer token, one of the server's `UPLOAD_TOKENS` |
| `project-name` | repository name | Application name shown in the dashboard |
| `project-version` | `github.ref_name` | Version label for the upload |
| `sbom-file` | `''` | Upload an existing CycloneDX/SPDX JSON file instead of generating one |
| `generator` | `syft` | `syft` scans the checkout with [Syft](https://github.com/anchore/syft); `dependency-graph` exports GitHub's dependency graph |
| `path` | `.` | Directory scanned by Syft |

Outputs: `project-id`, `sbom-id`, `url`. See [`examples/upload-sbom.yml`](examples/upload-sbom.yml).

The dashboard has to be reachable from the GitHub runner. For a dashboard on a private network, use a self-hosted runner.

### Uploading without the action

```sh
curl -X POST "http://localhost:3000/api/v1/sboms?project=my-app&version=1.2.3" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  --data-binary @sbom.cdx.json
```

Metadata can be passed as query parameters or `X-Sbom-*` headers: `project`, `version`, `ref`, `commit`, `repository`.
If `project`/`version` are omitted they are taken from the SBOM's subject (CycloneDX `metadata.component`, SPDX described package).

## Configuration

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | `postgres://sbom:sbom@localhost:5432/sbom` | Postgres connection string |
| `UPLOAD_TOKENS` | empty | Comma-separated bearer tokens required for uploads and deletes. Empty = open uploads outside production; in production uploads are rejected (503) |
| `ALLOW_OPEN_UPLOADS` | `false` | Set `true` to allow open uploads in production (e.g. `docker compose` on localhost) |
| `MAX_UPLOAD_BYTES` | 52428800 | Maximum SBOM size |
| `SBOM_HISTORY_LIMIT` | 20 | Uploads kept per application (older ones are pruned) |
| `WORKER_POLL_SECONDS` | 30 | How often the worker checks for due work (uploads also wake it immediately) |
| `VULN_TTL_HOURS` | 12 | Re-scan package versions for new vulnerabilities after this long |
| `LATEST_TTL_HOURS` | 24 | Re-check latest package versions after this long |
| `KEV_TTL_HOURS` | 24 | Re-download the [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) catalog (vulnerabilities known to be exploited) after this long |
| `EPSS_TTL_HOURS` | 24 | Re-check [FIRST EPSS](https://www.first.org/epss/) exploit-probability scores after this long (new CVEs are looked up immediately) |
| `EPSS_API_URL` | FIRST public API | Override for mirrors or testing |
| `KEV_URL` | CISA JSON feed | Override for mirrors or testing |
| `OSV_API_URL` / `DEPS_DEV_API_URL` | public APIs | Override for mirrors or testing |

The dashboard itself has no login yet; put it behind your network or a reverse proxy if needed.

## API

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/v1/sboms` | Upload an SBOM (token required when `UPLOAD_TOKENS` is set; disabled in production without one) |
| `GET` | `/api/v1/sboms/:id` | Download the original SBOM document |
| `GET` | `/api/v1/summary` | Totals, severity counts and recent uploads |
| `GET` | `/api/v1/projects` | Applications with their latest SBOM stats |
| `GET` | `/api/v1/projects/:id[?sbom=:sbomId]` | Application details and enriched packages |
| `DELETE` | `/api/v1/projects/:id` | Delete an application and its SBOMs (token required when configured) |
| `GET` | `/api/v1/packages` | Packages across all applications |
| `GET` | `/api/v1/packages/:key` | One package (key such as `npm%3Alodash`) |
| `GET` | `/api/v1/vulnerabilities[/:id]` | Vulnerabilities affecting the latest SBOMs |
| `GET` | `/api/healthz` | Health check (includes a database ping) |

## How the data is derived

- **Package identity:** from each component's [purl](https://github.com/package-url/purl-spec). Components without a purl are
  listed but can't be scanned or version-checked.
- **Vulnerabilities:** OSV.dev batch queries by purl and version. Severity comes from the CVSS v3 base score when present,
  otherwise from the advisory database's own rating. "Fixed in" is the smallest fixed version above the one in use.
- **Latest version:** deps.dev's default version for the package (npm `latest` tag, newest stable release elsewhere).
  Supported: npm, PyPI, Maven, Go, Cargo, RubyGems, NuGet.
- **Outdated:** the version in use compared to the latest. A different major version is a major update, a different minor is
  minor, anything else is patch.

## Development

```sh
pnpm run lint          # TypeScript, ESLint and Prettier check
pnpm run format        # apply Prettier
pnpm test             # Vitest: unit + API tests on in-process Postgres (PGlite), no database needed
pnpm run build && pnpm run test:e2e   # Playwright, needs Postgres; uses E2E_DATABASE_URL (default .../sbom_e2e), which it wipes
```

### Changing the schema

1. Edit `src/db/schema.ts`.
2. Run `pnpm run db:generate` to create a SQL migration in `drizzle/`. Review it and edit it if needed (e.g. data backfills).
3. Run `pnpm run db:migrate`.

CI fails if the schema changes without a matching migration.

### Layout

```
action.yml              GitHub Action (composite)
drizzle/                SQL migrations
scripts/                migrate, demo seed
src/app/                Next.js pages and /api route handlers
src/components/         MUI components (grids, charts, chips)
src/db/                 Drizzle schema and client
src/lib/                purl parsing, version comparison, CVSS scoring, env config
src/sbom/               CycloneDX / SPDX parsing
src/server/             ingestion and read model (queries + aggregation)
src/worker/             enrichment worker (OSV.dev, deps.dev)
tests/unit, tests/e2e   Vitest and Playwright suites
```

## Secret scanning

CI runs [gitleaks](https://github.com/gitleaks/gitleaks) on every push and PR. To catch secrets before they are committed, install it locally and add a pre-commit hook:

```bash
brew install gitleaks
printf '#!/bin/sh\nexec gitleaks protect --staged --redact\n' > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```
