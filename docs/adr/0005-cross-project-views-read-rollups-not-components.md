# Cross-project views read per-project rollups once measured to need them

We design for about 100 Projects of about 2,000 components each. This repo's own Syft SBOM has 1,975 components, so that is about 200k components in latest SBOMs and a few million `components` rows with `SBOM_HISTORY_LIMIT` (20) retained. `loadComponents()` into TypeScript is fine for one Project or one package, which `ComponentScope` already narrows, but not for the overview and projects grid on every request. Those will read per-Project rollups the worker writes beside `project_snapshots`; detail pages keep the scoped in-memory load, and remediation uses the scoped load per Project plus rollups for the cross-Project view.

This is gated on a benchmark (F-004) that seeds 100 Projects and records timings and table sizes, so the rollup (K-001) and the storage tickets (K-002, K-003) are built only for what the numbers show. Rejected: caching the in-memory load (stale and still O(inventory) on a miss), and pushing every aggregation into SQL (hard to test on PGlite and duplicates `aggregate*` logic). Worker concurrency (`FOR UPDATE SKIP LOCKED`) and an OSV change feed stay noted until the benchmark or an upload backlog says otherwise.
